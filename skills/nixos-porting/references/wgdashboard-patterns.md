# Patterns observed in WGDashboard

These techniques come from the inspected native port, not a requirement to clone its layout or operational defaults. The application is a Python server with two npm frontends and privileged WireGuard/AmneziaWG integration.

- **Separate build stages:** `nix/package.nix` builds both frontends with `buildNpmPackage` and locked dependency hashes, assembles immutable resources, and wraps Gunicorn using an explicit Python environment. Missing direct frontend dependencies were added to upstream manifests/locks; the build does not depend on a developer's node_modules.
- **Small runtime seam:** `DashboardEnvironment` separates asset and configuration paths with environment overrides. Defaults retain the original current-directory layout and interface-autostart behavior; tests cover both defaults and overrides. SQLite and other mutable paths use the state root; templates/locales use the asset root.
- **CLI compatibility:** network commands receive the full configuration path, allowing configurations outside traditional distribution directories without rewriting protocol implementations.
- **Actual lifecycle:** a dedicated Gunicorn configuration starts application/plugin background threads after worker initialization and keeps one worker. This is specific to the application's lifecycle, not a universal Python service template.
- **Bootstrap and reconciliation:** a separate initializer creates required state directories, merges declared non-secret INI fields, preserves omitted values, and hashes the initial password only when no password exists. The module passes the bootstrap password through `LoadCredential`; it is not an account-rotation mechanism.
- **Host-controlled implementations:** the module accepts protocol tool, kernel-module, and userspace packages from the consumer. It accounts for userspace device access and constrains mutable paths. These networking requirements should not be copied into unrelated web services.
- **Thin infrastructure adapter:** the inspected consumer uses a branch URL with a locked revision, makes the application's nixpkgs follow its own package set, and imports the exported module. Its local adapter supplies secret-manager paths, package choices, state locations, and startup policy. The consumer explicitly enables interface autostart while the reusable module defaults it off; operational policy stays outside the application fork.
- **Behavioral validation:** package install checks run initialization twice and validate the installed server configuration. A NixOS VM test verifies authentication, settings, existing-state preservation, permissions, configuration downloads, actual tunnel activation, and restart behavior with autostart disabled.
- **Independent patch purposes:** the local port follows an upstream development base and contains separate protocol-feature and NixOS commits. The default upstream branch differs from that chosen base. Establish both before evaluating patch size or planning a rebase.

The reusable lesson is to move build/install concerns into derivations and host lifecycle into a module while introducing only the runtime seams the application actually needs. This inspection establishes design patterns; it is not fresh evidence that the example builds or passes its VM tests at another revision.
